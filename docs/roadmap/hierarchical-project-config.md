# Hierarchical project configuration

Proposed implementation plan for `feature/hierarchical-project-config`, based on
`develop` at `d914e348`. The first deliverable is a read-only resolver for
`mana.toml` and a way for the operator to inspect its result.

## Operator experience

A team can configure an entire directory of projects once. A project needs its
own file only when it has project-specific settings. Use `mana.toml` so it can
live alongside the existing `.mana/` runtime directory.

For example, a personal registry binds the workspace root `work` to
`/work/repos`, the vault alias `engineering` to a local vault, and KB aliases
to read-only directories. Physical paths belong to the local machine. Below
that root the following files are optional. Each block shows one complete file.

`/work/repos/mana.toml`

```toml
version = 1
[export]
vault = "engineering"
[knowledge.sources]
common = true
personal = false
```

`/work/repos/payments/mana.toml`

```toml
version = 1
[knowledge.sources]
payments = true
[profiles.requested-pr-review]
runtime = "legacy"
```

`/work/repos/payments/ledger/mana.toml`

```toml
version = 1
[project]
id = "ledger"
[knowledge.sources]
ledger = true
```

From `ledger`, the proposed `./mana config explain` shows the vault from the
root, the review preference from the group, the project ID from the leaf and
the three enabled KB aliases. It identifies the declaring file for each
effective entry. The same root and group settings apply if the leaf is absent.

## Resolution contract

- Store machine bindings in `$XDG_CONFIG_HOME/mana/locations.toml`, falling
  back to `$HOME/.config/mana/locations.toml`. Keep this separate from the
  existing `config.env` User Context contract. Scope allowed vault and KB aliases
  to the registered root, including a separate opt-in for the personal KB.
- Resolve from the target project supplied by the launcher, even if the current
  shell directory differs. Select the most specific registered ancestor of
  its canonical path, then read only the direct `mana.toml` in each directory
  from that ancestor through the project, inclusive. A nested registered root
  starts a new scope. Outside registered roots, return the current defaults
  and explain why. The resolver never scans siblings or the whole home tree.
- Scalars use the nearest declaration. Merge KB choices by alias and skill
  preferences by profile and skill ID. An explicit false masks an inherited
  choice. Proposed skill syntax is `[profiles.<id>.skills]` with boolean
  entries. Preferences remain subject to profile eligibility and required
  skills. Project identity belongs to the leaf and is required only by a
  consumer that needs a stable identity, such as export.
- Express runtime selection as one value per profile (`legacy`, `v2` or
  `shadow`). Keep `compare` an explicit operation. For consumers introduced
  later, explicit invocation options take precedence over inherited preferences.
  Existing host admission and frozen rollout decisions still apply. Surface a
  conflict with those decisions before execution.
- Parse a versioned schema as data. Reject unknown keys, invalid types, duplicate
  declarations in one file, unsupported versions, symlinked configuration files
  and references outside the root's allowed aliases. A malformed nearer file
  yields a diagnostic identifying the file and key. Omitting all config files
  is a valid default configuration.

## Implementation sequence

| Step | Depends on | Change | Acceptance evidence |
|---|---|---|---|
| 1. Contract and parser | — | Specify and test project and machine schemas, including a minimal machine registry fixture. Confirm supported Python versions before choosing stdlib `tomllib` or a compatible parser. Avoid introducing a global Python upgrade for existing commands. | Example files parse. Unknown fields, invalid aliases, versions and malformed TOML fail with precise diagnostics. |
| 2. Shared resolver | 1 | Add one Python resolver under `scripts/lib/` returning effective settings, source per key and diagnostics. Keep discovery independent of consumers. | In temporary root/group/project fixtures, verify inheritance, override, false, absent leaf, nested roots, unregistered project and attempted escape. Resolving the same inputs from another working directory gives the same answer. |
| 3. Operator CLI | 2 | Add `config explain` and `--json` to the project launcher generated by `scripts/bootstrap-project.sh`, with direct invocation for framework development. Document how existing linked projects pick up the command. | Exercise the generated launcher on a linked fixture. Verify human and machine output, default behavior, failure exit and absence of writes or provider calls. Mark runtime, skill, KB and export values as configured preferences until their consumers exist. |
| 4. First consumer: manual Obsidian export | 3 | Let the operator explicitly export a completed transaction report and its diagram into the selected vault under a project-specific location. Begin with a preview listing source and destination files. Check the artifact set for machine-specific paths and keep associated links usable. | Use an ordinary temporary directory as the vault. Check isolation between projects, repeated export, destination collision, a user-edited note and interrupted publication. Preserve edited files and surface conflicts. |
| 5. Further consumers | 3 | Connect approved KB aliases to existing scoped retrieval on demand. Integrate skill and runtime preferences through existing profile selection and rollout code. Specify automatic export separately after evaluating manual use. | For KBs, verify provenance and exclusion of disabled/private sources. For profiles, verify explicit override, required skills, absent V2 pipeline and denied shadow execution. |

Steps 1–3 form the first implementation slice. Step 4 provides the first
end-to-end artifact workflow. Step 5 can be delivered per consumer.
